**Standards covered (2024 Virginia Computer Science SOL)**

- **5.AP.3** The student will use the iterative design process to create, test, and debug programs containing sequencing, loops, variables, user inputs, nested conditional control structures, and two-way branching conditional control structures in a block-based programming tool.
  - c. Trace and predict outcomes of programs.
  - d. Analyze and describe program results to assess validity of outcomes.
  - e. Revise and improve programs to resolve errors or produce desired outcomes.

## Prep

- Copy the student's program and add two errors, such as a reversed comparison and a variable that is not reset.
- Draw a test table: input, predicted outcome, actual outcome, valid?

## Warm-up (3 minutes)

Ask, "Before you run a program, how could you know what it should do?"

## Direct Instruction (4 minutes)

- Tracing a program: read the blocks in order, track the variables, and predict the result before running.
- Testing: choose inputs that reach every branch, including edge cases such as the smallest and largest allowed values.
- Validity: the outcome is valid when the actual result matches the correct expected result for every test.
- Revising: find the block responsible, change one thing, and rerun every test.

## Guided Practice (8 minutes)

1. The student traces the copy with errors for one input and predicts the outcome.
2. Run it and fill in the test table.
3. The student finds and fixes the first error and reruns the tests.
4. Repeat for the second error.

## Independent Practice / Quick Check (5 minutes)

The student writes three tests for their own program, including one edge case, predicts each outcome by tracing, runs them, and makes one improvement.

Look for:
- Predictions are made before running.
- Tests reach different branches.
- All tests are rerun after a change.

## Differentiation

**For students needing support**
- Add one error only.
- Trace with a finger on the blocks and the variable values written on paper.

**For students ready for more**
- Write a test that the current program fails, then fix the program.
- Explain why passing three tests does not prove a program is correct.

## Extensions

- Trade programs with someone and test each other's.
- Keep a version history noting each change and why.

## Notes for Parent/Instructor

- Edge cases are where errors hide. Ask, "What is the strangest input someone could give?"
- A fix that breaks something else is common. Rerunning all tests catches it.
