**Standards covered (2024 Virginia Computer Science SOL)**

- **4.AP.3** The student will use the iterative design process to create, test, and debug programs containing sequencing, loops, variables, user inputs, and conditional control structures in a block-based programming tool.
  - d. Analyze and describe program results to assess validity of outcomes.
  - e. Revise and improve programs to resolve errors or produce desired outcomes.

## Prep

- Make a copy of the student's program and add one error to the copy, such as a score that is never reset or a condition that is reversed.

## Warm-up (3 minutes)

Ask, "If your quiz gave a point for a wrong answer, how would you find out?"

## Direct Instruction (4 minutes)

- Introduce a test plan: a list of inputs to try and the result expected for each.
- Include different kinds of tests: a correct answer, a wrong answer, and something unexpected such as an empty answer.
- Define a valid outcome: the actual result matches the expected result for every test.
- Review the fixing routine: find the block responsible, change one thing, and run all the tests again.

## Guided Practice (7 minutes)

1. Write a three-row test plan for the quiz together.
2. Run the tests on your copy with the error. The student records actual results.
3. The student finds which test failed, locates the error, and fixes it.
4. Run every test again.

## Independent Practice / Quick Check (5 minutes)

The student writes one more test for their own program, runs the whole test plan, describes the results, and makes one improvement.

Look for:
- Each test has an expected result written before running.
- The student describes actual results and compares them with expected ones.
- After revising, all tests are run again.

## Differentiation

**For students needing support**
- Use two tests.
- Point to the general area of the error.

**For students ready for more**
- Test with unexpected input, such as capital letters or extra spaces, and decide how the program should respond.
- Ask someone else to try to break the program.

## Extensions

- Write a test plan for someone else's project.
- Keep a record of each version and what changed.

## Notes for Parent/Instructor

- Running all tests again after a fix catches new errors the fix may cause.
- A program that runs is not the same as a program that is correct. This lesson is about the difference.
