**Standards covered (2024 Virginia Computer Science SOL)**

- **7.AP.3** The student will use the iterative design process to create, test, and debug programs using a block-based or text-based programming language.
  - c. Analyze the outcomes of programs to identify logic and syntax errors.
  - d. Analyze and describe the results of a program to assess validity of outcomes.
  - e. Revise and improve an algorithm to resolve errors or produce desired outcomes.

## Prep

- Add three errors to a copy: one syntax error, one logic error in a condition, and one error in the function, such as a wrong calculation.

## Warm-up (3 minutes)

Ask, "What is the difference between a program that crashes and a program that quietly gives the wrong answer? Which is more dangerous?"

## Direct Instruction (4 minutes)

- Review syntax errors, which stop the program or produce an error message, and logic errors, which give wrong results.
- Teach a method for isolating errors: reproduce the error, narrow down where it happens by testing parts separately, form a guess, change one thing, and retest.
- Define validation: showing that results are correct for a set of planned test cases, including edge cases.
- Explain revising the algorithm, not only the code: if the plan was wrong, fix the plan too.

## Guided Practice (8 minutes)

1. The student runs the copy and resolves the syntax error using the message.
2. Run the test plan. Identify which tests fail.
3. Test the function alone to find its error.
4. Fix the remaining logic error and rerun all tests.

## Independent Practice / Quick Check (5 minutes)

The student writes a test plan of four cases for their own program, including two edge cases, runs it, records results, and revises anything that fails.

Look for:
- Errors are classified and located systematically.
- The test plan includes edge cases.
- All tests are rerun after revision.

## Differentiation

**For students needing support**
- Add two errors.
- Provide the test plan and let the student run it.

**For students ready for more**
- Write tests before fixing, so that a failing test proves the error exists.
- Explain an error where the algorithm itself was wrong.

## Extensions

- Debug someone else's program using the method.
- Keep a debugging log.

## Notes for Parent/Instructor

- A quiet wrong answer is the more dangerous error. Validation exists for that reason.
- Changing several things at once hides which change mattered.
