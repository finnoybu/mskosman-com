**Standards covered (2024 Virginia Computer Science SOL)**

- **6.AP.3** The student will use the iterative design process to create, test, and debug programs using a block-based or text-based programming language.
  - c. Trace and predict outcomes of programs.
  - d. Analyze and describe program results to assess validity of outcomes.
  - e. Analyze the outcomes of programs to identify logic and syntax errors.

## Prep

- Prepare three short programs: one correct, one with a syntax error (in text-based code, a missing colon or bracket; in a block tool, an incomplete block or empty slot), and one with a logic error such as a reversed comparison.

## Warm-up (3 minutes)

Write on paper: "Their going too the store." and "The store is going to them." Ask, "One has spelling mistakes and one makes no sense. Which is which?"

## Direct Instruction (5 minutes)

- Define syntax error: the code breaks the rules of the language, so it will not run, or the tool reports an error.
- Define logic error: the code runs but gives the wrong result because the instructions do not match the intent.
- Explain how each is found. Syntax errors are found from error messages. Logic errors are found by comparing actual outcomes with expected ones.
- Model a trace table and a prediction for the correct program.

## Guided Practice (7 minutes)

1. The student traces the correct program, predicts its output, and runs it.
2. Run the program with the syntax error. Read the message and fix it.
3. Trace the program with the logic error and predict what it will do. Run it and compare with what it should do.
4. The student classifies each error and explains how it was found.

## Independent Practice / Quick Check (5 minutes)

Give the student a fourth short program with one error of each kind. The student finds both, names the type of each, fixes them, and shows that the outcome is now valid.

Look for:
- Predictions come from tracing, not guessing.
- Errors are classified correctly.
- Validity is judged against a stated expected outcome.

## Differentiation

**For students needing support**
- Work with one error per program.
- Read error messages together and find the line they point to.

**For students ready for more**
- Find a logic error that appears only for certain inputs.
- Explain why tools can detect syntax errors automatically but not most logic errors.

## Extensions

- Introduce an error into a working program and challenge someone to find it.
- Keep a list of syntax errors you make most often.

## Notes for Parent/Instructor

- A program that runs without messages can still be wrong. That is the central point.
- In block tools syntax errors are rare. Discuss the idea using a text example if needed.
