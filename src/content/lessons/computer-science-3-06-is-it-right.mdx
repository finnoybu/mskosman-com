**Standards covered (2024 Virginia Computer Science SOL)**

- **3.AP.3** The student will use the iterative design process to create, test, and debug programs containing events, loops, and conditional structures in a block-based programming tool.
  - b. Analyze and describe program results to assess validity of outcome.
  - c. Revise and improve programs to resolve errors or produce desired outcome.

## Prep

- Build a short program with one error, such as a condition that checks the wrong thing or a loop that repeats too few times.
- Write down in one sentence what the program is supposed to do.

## Warm-up (3 minutes)

Ask, "If a calculator said 2 plus 2 is 5, how would you know it was wrong?" Lead to: you compare the result with what you expected.

## Direct Instruction (5 minutes)

- Define valid: "A valid outcome is a result that is correct for what the program was meant to do."
- Teach the check: 1. State the expected outcome. 2. Run the program. 3. Describe the actual result. 4. Compare.
- Explain that an error can be in the order of blocks, in a number, or in a condition.
- Model with your sample: read the goal sentence, run it, describe what happened, and find the block responsible.
- Revise one thing, then test again. "Change one thing at a time so you know what fixed it."

## Guided Practice (7 minutes)

1. The student runs your sample a second time and describes the result in their own words.
2. Ask, "Is that a valid outcome? How do you know?"
3. The student finds and fixes the error.
4. Turn to the student's own program. State its goal, test it, and describe the results.

## Independent Practice / Quick Check (5 minutes)

The student makes one improvement to their own program, tests it, and explains what the result was before, what it is now, and why the new outcome is valid.

Look for:
- The student compares actual results with expected results.
- The student changes one thing at a time.
- The revised program produces the intended outcome.

## Differentiation

**For students needing support**
- Use a sample with an obvious error, such as a wrong direction.
- Have the student act out the blocks to find where the result goes wrong.

**For students ready for more**
- Give a program that works for one input but fails for another.
- Ask the student to write three test cases before running the program.

## Extensions

- Swap programs with someone and test each other's work.
- Keep a bug journal: what went wrong, how it was found, how it was fixed.

## Notes for Parent/Instructor

- "Assess validity" is the new idea this year. It means checking results against the goal, not just checking that the program runs.
- Praise careful testing as much as a working program.
