**Standards covered (2024 Virginia Computer Science SOL)**

- **8.AP.3** The student will use the iterative design process to create, test, and debug programs using a block-based or text-based programming language.
  - d. Analyze and describe the results of a program to assess validity of outcomes.
  - e. Revise and improve an algorithm to resolve errors or produce desired outcomes.

## Prep

- Arrange for someone to test the program.
- Prepare a test plan template: case, input, expected result, actual result, pass or fail.

## Warm-up (3 minutes)

Ask, "How many tests are enough to say a program works?"

## Direct Instruction (4 minutes)

- Define validity: results are correct and meet the purpose stated in the scoping document.
- Teach test design: typical cases, edge cases at the boundaries, and invalid input.
- Explain describing results: state what happened precisely, with values.
- Explain revising the algorithm: when a test fails, decide whether the code or the plan is wrong. Update both. Rerun all tests after any change.

## Guided Practice (9 minutes)

1. The student writes a test plan of at least six cases.
2. Run the plan and record results.
3. A tester uses the program while the student observes.
4. Choose the most important failure and revise the algorithm and code.

## Independent Practice / Quick Check (4 minutes)

The student reruns the full test plan, makes a second revision if needed, and writes a summary: what was tested, what failed, what was changed, and why the outcomes are now valid.

Look for:
- The test plan covers typical, edge, and invalid cases.
- Results are described with specifics.
- Revisions are followed by full retesting.

## Differentiation

**For students needing support**
- Write four test cases.
- Revise one failure together.

**For students ready for more**
- Automate a test by writing code that checks a function's results.
- Measure the program against the original purpose and identify what is still missing.

## Extensions

- Publish or share the finished program.
- Write release notes describing the changes.

## Notes for Parent/Instructor

- No number of tests proves a program correct. Good tests make errors unlikely.
- This lesson completes the design cycle for the project.
